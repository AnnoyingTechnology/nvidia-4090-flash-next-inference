## Next agent: ideas to assess, not experiments already started

1. Explain the remaining decode critical path before sweeping knobs. Real
   OpenCode logs put decode at 70.3% of engine time and prefix reuse at 97%.
   CPU-expert timing overlaps GPU work; summed stages can double-count.
   `STRATA_DECODE_TIMING` gives per-request aggregate timing. Instrumented
   `STRATA_VERIFY_PROFILE` clocks add work; `--stage-timing` reports kernel-count
   shares, not wall time. A valid GPU floor is `--gpu-only-full`, not
   `--graph-only` (which omits post-layer/head work). Do not use diagnostic
   builds as production-speed evidence.
2. Investigate why cache-hit/MTP acceptance and the gain differ by request
   prefix. Select a small reusable agent workload with frozen inputs and
   useful natural completions. Avoid selecting only favorable speed cells.
3. Vision context retention might remove 20–30 ms of initialization; deferred
   adaptive filling of empty cache-tail slots might remove 40–60 ms of reclaim.
   Both are **unbuilt hypotheses**; deferred refill touches the hot path.
   The owner already accepts current latency, so do not make them prerequisites.
4. Broader repository/tool and reviewed visual-arithmetic canaries remain more
   useful quality work than rescuing capped contests. Use published paired
   full-size results; local Q4 is a trade-off candidate, not a reference oracle.
5. ExLlamaV3/TabbyAPI, a supported R550-compatible alternative bootstrap and
   the planned multi-3090 R&D machine remain unqualified alternatives. DeepSeek
   4.1 Flash is a separately planned experiment; the 397B fit probe is only
   about 12.4 tok/s with quality unqualified. See [research](research-and-pitfalls.md).

**Closed without new evidence:** eddoursul fork (measured slower, owner closed);
